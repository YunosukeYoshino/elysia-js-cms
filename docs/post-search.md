# 投稿検索・公開予約

`GET /api/posts` は既存の `data` / `meta.total` / `meta.take` / `meta.skip` を維持し、検索情報を追加します。`GET /api/categories/:id/posts` も同じ投稿サービスを利用します。

## クエリ

- `q`: タイトル・本文の全文を対象にしたリテラル部分一致検索。最大200文字、空白で区切った異なる検索語は最大10個です。各語がタイトルまたは本文に存在する投稿だけを返します（語同士は AND）。英字ASCIIは大文字小文字を区別しません。日本語なども部分一致で検索できます。
- `sort`: `relevance` / `newest` / `oldest`。`q` 指定時は関連度順、それ以外は新着順です。関連度は各検索語のタイトル一致に3点、本文一致に1点を加算します。同点の場合は作成日時、IDの順で安定的に並べます。`relevance` には `q` が必要です。
- `authorId`: 著者ID。
- `categoryId`: 既存の単一カテゴリ指定。`categoryIds` と併用できません。
- `categoryIds` / `tagIds`: 正の整数IDをカンマで列挙（各最大20個）。同じリスト内は OR、異なるフィルター間は AND です。重複IDは除去します。
- `createdFrom` / `createdTo`: 作成日時の両端を含む範囲。UTCの `YYYY-MM-DD` または `YYYY-MM-DDTHH:mm:ss[.SSS]Z` 形式です。日付のみの終了値は当日23:59:59.999まで含みます。存在しない日付、逆転した範囲、UTC以外のオフセットは422です。
- `status`: `draft` / `published` / `scheduled`。
- `published`: 従来の `true` / `false`。有効な公開状態を表し、`false` は下書きと未到来の予約を含みます。`status` とは併用できません。
- `take` / `skip`: 既存のページ契約（省略10/0、0件、負のtakeによる逆方向取得）を維持します。新規パラメーター（`q`、`status`、複数カテゴリ、タグ、日付、`sort`）を指定した検索は `|take| <= 100`、`skip <= 10000` に制限します。従来のパラメーターだけを使うクライアントのページ上限は変更しません。

不正な整数・空値・制御文字・未知の状態などは、SQL実行前に422で拒否します。`%`、`_`、引用符、SQL/FTS演算子は特殊構文として展開しません。

例:

```text
/api/posts?q=bun%20sqlite&authorId=1&categoryIds=2,3&tagIds=5&createdFrom=2026-01-01&createdTo=2026-12-31&status=published&take=20
```

## レスポンス

投稿の `author` は `{ id, name }` のみを返します。旧レスポンスに含まれていた `author.email` は、著者の個人情報を保護するため意図的に削除しました。一覧・詳細・カテゴリ経由・検索・作成/更新レスポンスで共通の契約です。匿名利用者、著者本人、管理者のいずれにもメールアドレスは含めず、閲覧可能な非公開投稿も同じ契約を使用します。著者ファセットは `{ id, name, count }`、著者のフィルター選択肢は `{ id, name }` のみです。本人のメールアドレスは引き続き認証済みの `GET /api/auth/me` で取得できます。認証・アカウント用レスポンスの契約は変更しません。

投稿に `status`、`scheduledAt`、`tags: [{ id, name }]` を追加します。`q` があれば `relevance` と `highlights: { title, content }` も返します。ハイライトは一致付近の短い抜粋（タイトル最大300、本文最大240 UTF-16コード単位）で、一致を `<mark>` で囲みます。投稿本文と検索語のHTMLはエスケープ済みです。元の `title` / `content` 自体は加工しないため、画面では通常のテキスト表示または適切なHTMLサニタイズを使用してください。

`meta.filters` は正規化済みの指定条件、`meta.facets` は現在の条件に一致し閲覧できる投稿の件数です。ページング前の集合で集計するため、ページを変えても件数は同じです。カテゴリ、タグ、著者にはID・名前・件数、状態には `value`・件数を含みます。1投稿の複数関連による二重計上を避けています。

`meta.filterOptions` はその集合に存在する選択肢です。非公開投稿だけに存在する著者やタグを匿名利用者に開示しません。カテゴリ・タグ・著者の各ファセットは件数降順、ID昇順の上位100件で、`facetLimit` と `facetsTruncated` で打ち切りを示します。指定済みのフィルターも集計に反映する「絞り込み後」の件数です（対象ファセット自身の条件を除外する方式ではありません）。空集合では選択肢は空で、状態件数は0になります。

## タグと予約の作成・更新

投稿のPOST/PUTに `tags: ["Bun", "SQLite"]` を渡すとタグを自動作成・再利用します。タグ名は前後空白除去、NFKC正規化、小文字化し、重複を除きます。最大20個、正規化後1〜50文字です。省略すると既存関連を維持し、空配列なら全タグを外します。カテゴリ置換とタグ置換は投稿本文の更新と同じトランザクションで行い、存在しないカテゴリなどで失敗した場合は全体を戻します。

- 下書き: `published: false`、`scheduledAt: null`
- 即時公開: `published: true`（既存予約を解除）
- 予約: `scheduledAt: "2099-01-01T09:00:00Z"`（未来のUTC日時。公開フラグはfalse）
- 予約解除: `scheduledAt: null`
- 公開取り消し: `published: false`（予約も解除）

`published: true` と非nullの予約日時を同時指定すると422です。予約日時だけを変更すると公開フラグはfalseになります。予約・公開設定を省略した更新は既存設定を保持します。

予約時刻に達すると、読み取り時の判定で自動的に公開として扱います。別のジョブは不要です。保存済み `published` がfalseのままでもAPIの `published` はtrue、`status` は `published` になります。外部でDBを直接読む場合も同じ判定（`published = true OR scheduledAt <= now`）を利用してください。

匿名利用者は公開済みだけ、認証済み著者は公開済みと自身の非公開投稿、管理者は全投稿を参照できます。権限のない詳細取得は404を返し、検索件数やファセットも同じ制約に従います。カテゴリ経由の一覧でも同じ制約です。投稿の変更・削除には引き続き著者または管理者権限が必要です。

## DBと性能

追加マイグレーション `20261006182100_post_search` は既存コンテンツを変更せず、予約列、タグ・中間テーブル、公開状態/作成日時/著者/予約日時/関連IDの索引を追加します。新しいPrismaクライアントを生成してください。開発の `prisma db push` でも同じ機能を使用できます。既存環境は変更前にバックアップし、その環境の既存マイグレーション履歴を確認してから適用してください。

今回の実装はPrismaのパラメーター化SQLとSQLite標準の `instr` / `lower` を使用します。FTS5専用テーブル・トリガーを追加しないため、既存の `db push` 運用でも検索索引の同期漏れがありません。ページのID・関連度・並べ替え・件数・ファセットをDB内で計算し、本文と関連オブジェクトは取得ページ分だけロードします。検索結果と集計は同じ読み取りトランザクションから返します。

リテラル全文走査のため大規模コーパスには限界があります。ステミング、自然言語形態素解析、ASCII以外の大文字小文字同一視、BM25、引用句構文は提供しません。検索語上限・検索ページ上限・ファセット上限を設け、カテゴリ/著者/日付で候補を減らせます。1000投稿と105タグでページング、安定順、集計、ファセット上限を回帰テストしています。将来FTS5/MeiliSearchへ置き換える場合も、サービスの条件・可視範囲・レスポンス契約を維持してください。
